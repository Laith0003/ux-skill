# design-systems

- **Solve each recurring problem once, then reuse the solution.** Every extra header style, button or color adds code, slows pages and splits the experience; pick one answer and keep it until a deliberate change replaces it. Confidence: high. Sources: B22 p.15-16; B47 p.29-32; B07 p.14; B79 p.156, 159; B62 p.166
- **Stay consistent unless the new way is clearly better for the user.** Consistency lets people learn once; break it only when a variation makes something markedly clearer or when the behavior really differs, and aim for cohesive rather than identical. Confidence: high. Sources: B79 p.156, 159, 161, 246; B77 p.44; B07 p.267-268; B27 p.133-134
- **Draw every low-level value from a short predefined scale.** Spacing, color, type size, line height, weight, border, radius, shadow, opacity and width each draw on a small set of options fixed in advance (an icon scale of 12, 16, 24, 32 px is one example). Confidence: high. Sources: B47 p.29-32; B85 p.151-152, 168-169; B27 p.186-187; B34 p.91-92
- **Treat the system as docs, rules and code in one source of truth.** A design system is the single reference for the presentation layer, shipping code, design assets and wireframe parts for every element so teams assemble screens from it rather than redraw them. Confidence: high. Sources: B34 p.84-85, 89-90; B62 p.33; B59 p.3; B89 p.377, 383, 393
- **Judge the system by whether the coded product matches the library.** The real measure is that production mirrors the design library and teams reuse existing parts instead of inventing new ones. Confidence: medium. Sources: B22 p.25; B46 p.151
- **Expect written standards alone to be broken often.** Measured compliance with guideline documents runs low (roughly 70 percent at best, with mandatory rules broken a third to a half of the time), so ship reusable code, examples and checks rather than rule lists. Confidence: high. Sources: B46 p.151; B89 p.383, 393; B62 p.33
- **Name tokens by purpose and alias them to base values.** A role name such as a light background token can be retuned safely, while a literal value name used everywhere cannot; keep base values and purpose aliases as separate layers. Confidence: medium. Sources: B22 p.184-192; B07 p.179-180
- **Ship text and background color pairs already checked for contrast.** Color tokens should state which text color is legible on each background, alongside the type scale and fallback font stacks. Confidence: medium. Sources: B07 p.179-180; B80 p.129; B18 p.60-61
- **Fix accessibility once in the shared templates and components.** Contrast, visible focus, link states, skip links and heading structure built into the theme are inherited by every product built from it. Confidence: medium. Sources: B18 p.60-61; B91 p.175, 205-206
- **Annotate accessibility intent before handoff.** Mark headings, landmarks, reading order, contrast, non-color cues, focus visibility and keyboard behavior so they become acceptance criteria and automated tests. Confidence: medium. Sources: B91 p.175, 205-206; B80 p.129
- **Codify tokens and copy, not only widgets.** Record the palette and state colors, the grid, type weights and sizes, voice rules, a banned-word list, and the standard labels for buttons and navigation. Confidence: medium. Sources: B34 p.91-92; B35 p.270-274; B78 p.84-89; B55 p.173-174
- **Document the why, when and how, not just the appearance.** For each component record intent, behavior, edge cases and when to choose one variant over another; specs and screenshots alone hide these. Confidence: medium. Sources: B22 p.199-209; B93 p.457-460; B62 p.292-295
- **Give every component a fixed documentation record.** Title, code, picture, short overview, status, use when and do not use when, plus guidelines, then visual style, code, accessibility notes and metrics as needed. Confidence: medium. Sources: B62 p.292-295; B22 p.199-209
- **Explain every do and don't example in words.** A good or bad image without a sentence on what is right or wrong teaches nothing reliable. Confidence: low. Sources: B22 p.209-211; B89 p.377
- **Deliver guidance as task-indexed examples with reusable code.** Developers copy working products rather than read guideline lists, so pair good and bad examples, rationale and code. Confidence: medium. Sources: B89 p.377, 383, 393; B62 p.33
- **Promote a component only after it recurs.** Something used once or twice is not yet a pattern; add it when reuse or duplicates appear and when it is stable, distinct from existing variants and easy to explain. Confidence: medium. Sources: B07 p.163-164; B62 p.191-193, 199
- **Limit choices rather than cover every widget.** A deliberately smaller component set is easier to maintain and keeps output coherent, including UI that a model assembles from the catalog. Confidence: medium. Sources: B34 p.86; B16 p.39, 197, 207
- **Describe each component by the user intent it serves.** When software or an LLM selects UI, a catalog entry that says which intent it answers (browse, compare, locate) maps requests to components directly. Confidence: low. Sources: B16 p.203-204
- **Lock component styling and expose content and permitted options.** Library parts should let designers change text and approved variants but not font, color, radius or height. Confidence: medium. Sources: B22 p.158, 177; B59 p.16
- **Offer enough variants that people do not route around the system.** Provide sizes, solid and outline styles and multi-select forms, while keeping global navigation and footer fixed. Confidence: low. Sources: B22 p.112-113
- **Keep component markup and styles encapsulated.** Use a standard module structure (container, head, body, foot), scope CSS and scripts to the component and avoid inline or presentational styles so it can be reused with other schemes. Confidence: medium. Sources: B62 p.176-178, 235; B59 p.16
- **Build one card or module template that resizes for viewport and content length.** A shared template keeps a series consistent while each item still carries its own content. Confidence: medium. Sources: B88 p.246-247; B71 p.119, 162
- **Size template slots to the content they will receive.** Give each slot an example and a character limit; a slot designed for 100 characters breaks when 500 arrive. Confidence: low. Sources: B39 p.82, 121-122
- **Start from audited problems, not visuals.** Inventory every distinct variant (size, spacing, color, case, radius, shadow, icon, hover, error) and where it lives, ask what each is for, then collapse near-duplicates into a defined set. Confidence: medium. Sources: B22 p.117-120, 128-135; B07 p.14
- **Agree one layered model and plain shared vocabulary early.** Foundations, components, patterns, then templates and pages, with defined terms, so design and engineering stop arguing over names. Confidence: medium. Sources: B22 p.89-93, 102-103; B62 p.25; B74 p.174-175
- **Turn any repeated group into a linked master.** Anything that will change or vary should be a symbol so one edit updates every screen; embed only parts stable for the project. Confidence: low. Sources: B74 p.58, 121, 145; B62 p.97-98, 115-116
- **Version, deprecate and log every change.** Use semantic versioning, flag deprecated parts, keep retired codes retired, and publish a changelog with the reason and screenshots. Confidence: medium. Sources: B07 p.188-192; B62 p.199-200, 264-267; B22 p.276-278
- **Update library, code, docs and team in one move.** A change to any element updates the design library, queues the code change, updates documentation and is announced. Confidence: low. Sources: B22 p.276-278
- **Track component lifecycle status explicitly.** Move parts through drafted, reviewed, published, deprecated and retired, and label releases as test, pilot or active. Confidence: low. Sources: B62 p.264-267
- **Give the system an owner, a request channel and a cadence.** A named curator or team, one front door for requests and a predictable release cycle (for example four weeks) keep it alive and stop ad hoc demands. Confidence: medium. Sources: B34 p.89; B62 p.271, 275; B55 p.173-174
- **Build the system alongside a product team that uses it.** Pairing the system team with an application team keeps components grounded in real needs. Confidence: medium. Sources: B34 p.87-88
- **Adopt a formal library only when scale justifies it.** Small co-located teams can rely on conversation; a library pays off once stable grid, type and chrome exist and the catalog passes about 20 to 30 items. Confidence: low. Sources: B62 p.155-157, 210; B07 p.159
- **Preview components on a neutral ground with real data and states.** Show reversed, small-screen and every state, loaded with real content, to expose limits; an all-elements, all-states page doubles as a QA canvas. Confidence: medium. Sources: B07 p.157, 164-166; B78 p.84-89; B74 p.174-175
- **Keep the same lightness intervals across every colorway.** When a design ships in several color versions, matching areas should keep the same contrast, which may mean shifting the whole palette lighter or darker. Confidence: medium. Sources: B70 p.43
- **Specify colors by exact values on a named, ordered scale.** Descriptive names drift and are imagined differently; tokens carry exact values on a graded scale of a manageable size (about 12 hues is the limit people can hold). Confidence: medium. Sources: B70 p.30-31; B53 p.106, 419-421
- **Document unsafe token pairings and context shifts.** Record which combinations fail together and which values change by context so nobody rediscovers them. Confidence: low. Sources: B53 p.194, 293
- **Treat motion as tokens: an easing palette and duration presets.** One shared default curve, a distinct curve for destructive or high-stakes moments, durations on a common multiple (such as 100 ms) and named patterns stop teams inventing variants. Confidence: medium. Sources: B42 p.121-123, 199-207
- **Hand off animation with written duration, easing, delay and iteration count.** A video hides these values; developers need them as numbers. Confidence: low. Sources: B42 p.214-215
- **Split editorial guidance into style and tone, embedded where people write.** Style covers abbreviations, capitalization, numbers and preferred terms; tone covers person, tense and call-to-action wording; put both next to the CMS fields. Confidence: medium. Sources: B39 p.121-122; B55 p.173-174
- **Design elements that survive change of scale and new uses.** Avoid features that date quickly and keep one constant treatment across a varied series. Confidence: low. Sources: B71 p.119, 132

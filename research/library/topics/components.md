# components

- **Use buttons for actions and links for navigation.** A link that triggers an action, or a clickable div or span, confuses people and is not keyboard focusable or announced as a control; use a button element for actions and an anchor with an href for navigation. Confidence: high. Sources: B26 p.622-623; B80 p.42-45; B23 p.465; B22 p.260
- **Rank actions visually: one primary, then secondary and tertiary.** Give the main action a solid high-contrast style, secondaries an outline or low-contrast style, tertiaries a link style, and keep one or two primary buttons per page; equal-weight buttons force people to read them all. Confidence: high. Sources: B47 p.60-61; B22 p.135-137, 260; B24 p.190-191, 373-375; B26 p.622-623
- **Specify every state, not just the default.** Default, hover, focus, active or pressed, disabled, error, loading, empty, selected and post-submit states must be designed; handoffs that omit them leave developers to guess. Confidence: high. Sources: B22 p.108, 178-180, 228-231; B14 p.56-57; B62 p.59-60
- **Give every focusable element a visible focus style distinct from hover.** Do not rely on a browser default outline that a reset may remove. Confidence: high. Sources: B80 p.80-81; B91 p.242; B18 p.60-61
- **Prefer native controls or a tested library over custom widgets.** A custom select must reproduce Space, arrows, Page keys, Escape, type-ahead and ARIA roles; most teams should not build one. Confidence: high. Sources: B80 p.46-48; B22 p.96-97; B52 p.147
- **Make custom touch controls behave exactly like native ones.** A tap allows little movement and completes on release within about 300 ms, and sliding off before release cancels it; any deviation erodes trust. Confidence: medium. Sources: B52 p.147
- **Expose component state to assistive technology, not only through classes.** Accordion triggers are buttons with aria-expanded and aria-controls; breadcrumbs and pagination sit in a labelled nav with aria-current set on the current page; custom elements need tabindex 0 (never positive values) and key handlers. Confidence: medium. Sources: B91 p.242, 248, 250, 251; B80 p.91-96
- **Move focus into a dialog and return it on close.** Save the triggering element, focus the dialog or its first control on open, keep Tab inside a full-screen modal, hide the page behind it from assistive technology, and restore focus to the trigger when it closes. Confidence: medium. Sources: B80 p.81-85
- **Give every dialog an accessible name, a labelled close button and Escape.** Use role dialog (alertdialog when a response is required) with aria-labelledby on the heading; a div with an X glyph is neither focusable nor reliably announced. Overlay click may close it unless an answer is required. Confidence: medium. Sources: B80 p.78-80, 82-87; B51 p.175, 252-253
- **Put focus back after a single-page app redraws.** When a sort or filter rebuilds the DOM, move focus to the matching element instead of letting it fall to the top of the page. Confidence: low. Sources: B80 p.96-98
- **Show options as radio buttons or check boxes when people must compare them.** Visible option sets were faster, more accurate and preferred even up to about 30 items; use a drop-down only when space is short and the default is usually right. Confidence: high. Sources: B46 p.497-500, 571-576
- **Choose the control from the data and the number of states.** A button for one action, a switch for two states, a segmented set or dial for a few discrete states, a slider for a continuous range, a combo box when typing beats picking, a text field for unbounded input. Confidence: high. Sources: B14 p.47-48; B46 p.533-546, 578-580
- **Never use selection controls to trigger commands.** Radio buttons, check boxes and scroll bars set state; actions come from buttons. Confidence: medium. Sources: B46 p.499, 556; B26 p.594-598
- **Keep control idioms intact.** Check boxes stay square and radios round, a lone radio should be a check box, a switch labels both states, and a button whose icon flips between play and pause is ambiguous between state and action. Confidence: medium. Sources: B26 p.594-598; B22 p.96-97
- **Keep standard controls looking standard.** A select restyled to look like a button or decoration gets missed. Confidence: medium. Sources: B22 p.96-97; B52 p.224-225
- **Give controls with different jobs a distinct look and feel.** A row of lookalike controls invites slips; vary their shapes, separate or group the ones people confuse, and keep destructive controls away from frequently used ones. Confidence: medium. Sources: B79 p.142, 180, 204; B46 p.479-485
- **Separate running a command from configuring it.** A command button acts at once with the last settings; configuration lives in a linked dialog, since commands are run about ten times for each configuration. Confidence: medium. Sources: B26 p.292-294, 662
- **Label buttons with the specific outcome, not Yes or No.** Write the action (Save and exit, Exit without saving), and use Stop rather than Cancel when the previous state cannot be restored. Confidence: medium. Sources: B46 p.360, 441, 603-604; B26 p.638-639
- **Order dialog buttons predictably and default to the safe choice.** The default is the most likely and least destructive action; for deletes, Cancel becomes the default; never relabel Cancel to Close on the fly. Confidence: medium. Sources: B46 p.479-485; B26 p.638-639, 659-661
- **Do not make destructive actions big and red by default.** When delete is not the page's main task, style it as secondary or tertiary and reserve bold red for the confirmation step. Confidence: medium. Sources: B47 p.62; B46 p.479-485
- **Gray out unavailable options instead of letting errors happen later.** Disabling items that cannot be used at this stage prevents wrong choices before they are made. Confidence: medium. Sources: B02 p.55
- **Keep tabs few, short and on one row.** Reserve tabs for under about 10 similar modules labeled in one or two words, never stack tab rows, and show the active tab by connecting it visually to its panel rather than by color alone. Confidence: medium. Sources: B86 p.242-243; B26 p.659-661
- **Group buttons in sets of two to five.** Split a group once it passes three or four actions, show at most two inline actions per list row and move the rest behind a reveal or More. Confidence: medium. Sources: B86 p.384-386; B24 p.197; B46 p.478-479
- **Keep menus to about 8 items and one cascade level.** Menus of 5 to 10 items, ideally 8 or fewer, with cascades at most two levels and preferably one; vertical lists scan about 20 percent faster than horizontal ones. Confidence: medium. Sources: B46 p.238, 402, 405-408
- **Size tooltips and delay them deliberately.** Show a hover label after the pointer rests about 0.75 to 1 second and keep tip text to about 100 characters. Confidence: medium. Sources: B46 p.565, 568; B02 p.242
- **Pair icons with text labels, especially for critical or uncommon actions.** Unlabelled icons are often misread (one study found 44 percent recognition); labels help on small sets and should appear on hover or focus for large toolbars. Confidence: high. Sources: B08 p.209, 327-332; B02 p.239-242; B86 p.279, 378; B52 p.224-225
- **Prefer literal, direct icon mappings over arbitrary symbols.** Context-specific, pictorial icons that resemble the object are recognized far better than general or abstract ones. Confidence: medium. Sources: B02 p.239-242; B08 p.329-331
- **Use the platform's exact icon for standard actions, one icon per meaning.** Near-miss icons breed doubt; never give one icon two meanings, two icons one meaning, or reuse a standard icon for something new. Confidence: medium. Sources: B52 p.224-225; B86 p.279
- **Draw an icon set in one style.** Match stroke weight, corner treatment and fill style across every icon. Confidence: medium. Sources: B86 p.279, 378; B05 p.135, 222-223
- **Choose icon objects that look the same in every culture and keep text out of them.** An envelope, not a local mailbox; avoid flags, faces, gestures, puns and lettering inside the graphic, and keep any needed text in a separate translatable layer. Confidence: medium. Sources: B08 p.47, 186-188, 201-207; B49 p.75, 263-264
- **Use icons and images at the size they were drawn.** Icons made for 16 to 24 px look chunky at three or four times scale; enclose small icons in a shape instead, and redraw favicons at 16 px. Confidence: low. Sources: B47 p.208-213
- **Use uniwidth type where a label changes weight on state.** In uniwidth families every weight has the same character widths, so an active menu item or button can turn bold without shifting layout. Confidence: medium. Sources: B88 p.54-55
- **Make dismiss controls obvious and large enough to hit.** A tiny or hidden close button on prompts and recommendations obstructs; a 10 px checkbox needs a clickable label to be usable. Confidence: low. Sources: B51 p.175, 252-253; B80 p.51
- **Define components as independent chunks sized by what varies together.** Keep a control with the thing it controls, and split stacked blocks whose states change independently into separate components; components typically cover 70 to 80 percent of a page. Confidence: low. Sources: B62 p.9, 37-43, 52
- **Prefer one shared component that meets most needs.** One common player or widget covering about 90 percent of cases beats a custom one per page. Confidence: low. Sources: B62 p.85
- **Define a repeating component once and add count rules.** Skip building distinct variants for groups of three, four or five; document a single instance plus limits on quantity and layout. Confidence: low. Sources: B62 p.89, 117
- **Show variations side by side, default first, plus what is forbidden.** Order variations to show growth (empty, one, many), render a few rich examples instead of every combination, and include invalid uses as visual don'ts. Confidence: low. Sources: B62 p.61-67, 136, 294
- **Treat a change of markup as a new variation.** Examples may only change content; if a sample needs different tags or CSS it is a separate variation or component. Confidence: low. Sources: B62 p.206-210
- **Name patterns and use the names everywhere.** A shared name for each variant beats descriptions in design files, code, tickets and conversation. Confidence: low. Sources: B22 p.107, 136
- **Document what, where and when for each component.** Record appearance with minimum and maximum sizes, standard placement and when to choose it over an alternative. Confidence: medium. Sources: B34 p.91; B62 p.59-60
- **Merge functions into a single control for frequent actions, except where mistakes are expensive.** Frequent actions benefit from apparent simplicity; expensive ones (mute) keep their own control, and rare tasks expose every option. Confidence: medium. Sources: B14 p.91

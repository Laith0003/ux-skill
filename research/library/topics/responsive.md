# responsive

- **Make content reflow at 320 CSS px and at 200 to 400 percent zoom without horizontal scrolling.** WCAG 1.4.10 requires single-direction scrolling at a 320px width (equal to 1280px at 400 percent zoom), and text enlarged to 200 percent must stay linear and readable; overlapping or clipped text at larger sizes is a defect. Confidence: high. Sources: B91 p.115, 149, 158, 245, 263; B18 p.129-131; B59 p.11
- **Never block pinch zoom.** Users with low vision and anyone reading small text rely on it; a viewport that disables scaling fails them. Confidence: medium. Sources: B77 p.161; B91 p.115, 245
- **Design the smallest screen first, then enhance upward.** Starting from a phone canvas of about 360 to 400px forces real priorities; add layout for larger screens rather than squeezing a desktop design, and never withhold content from small-screen users. Confidence: medium. Sources: B85 p.128-131; B47 p.78-79; B38 p.29
- **Place breakpoints where the layout breaks, informed by real traffic.** Resize until the design strains and add a breakpoint there, checking your own analytics for the most common widths, rather than targeting named device classes. Confidence: medium. Sources: B85 p.129-130; B11 p.120; B74 p.143, 164
- **Size type and layout in relative units.** Rem, em and percentage widths let a fluid grid keep its proportions when users enlarge text; convert by dividing target by context (24px on a 16px base is 1.5). Confidence: medium. Sources: B18 p.129-131; B88 p.44
- **Shrink large type faster than small type on phones.** A desktop headline-to-body ratio of about 2.5 should fall to about 1.5 to 1.7 on mobile, so set headline sizes per breakpoint or with fluid clamps instead of as fixed multiples of body. Confidence: medium. Sources: B47 p.92-94; B88 p.244-245
- **Let type settings change fluidly with the container.** Fluid or intrinsic typography can scale size, optical size, line height and other variable axes gradually between breakpoints. Confidence: low. Sources: B88 p.244-245
- **Cap component widths with max-width, not column spans.** Column-based widths can make a card narrower on a large screen than on a medium one; give it a maximum width and shrink only when the viewport forces it. Confidence: low. Sources: B47 p.88-90
- **Keep crucial content visible in the worst case.** Design the grid so key content is never cropped or pushed out on small screens; hierarchical grids that vary column widths handle changing content and viewports best. Confidence: medium. Sources: B92 p.108; B10 p.106
- **Structure content as separate fields so it can adapt per context.** Store headline, short abstract (about 50 characters), lead image and body separately so each surface shows the right amount; serve different content only when a context truly needs it. Confidence: medium. Sources: B39 p.99-100; B35 p.114-115, 228-229
- **Deep-link shared URLs to the actual content on every device.** Never redirect a shared link to the mobile home page, and keep tasks and look consistent across devices so switching does not erode trust. Confidence: medium. Sources: B77 p.161; B40 p.62; B71 p.120, 132
- **Decide the responsive strategy during wireframing.** Agree with developers on reflow versus device-specific layouts before page structure hardens, and design navigation for small screens on its own terms. Confidence: low. Sources: B38 p.29; B74 p.97-105
- **Prototype both states of patterns that change across widths.** Accordions on narrow screens that become tabs on wide ones, and stacks that become side-by-side panels (for example above about 1024px), need each state designed. Confidence: low. Sources: B74 p.88-89; B26 p.585
- **Test motion at the smallest and largest viewports.** Movement-based animation can break as viewports change, while opacity, blur and color effects usually survive. Confidence: low. Sources: B42 p.225-226
